# NKMM_COMMAND_PALETTE_ROMAJI_KANJI_JIS1TABLE 実装レポート

対象フラグ: `NKMM_COMMAND_PALETTE_ROMAJI_KANJI_JIS1TABLE`(新規、既定は無効)
対象ファイル(主なもの):

- `sakura_core/util/CKanjiReadingTableJIS1.h`(新規。JIS第1水準漢字2965字の
  音訓読み全件テーブル)
- `sakura_core/util/CFuzzyMatchJp.cpp`(`FindReadingFromJIS1Table()`/
  `ExpandKanjiReadings()`)
- `sakura_core/util/CKanjiReadingDict.cpp/.h`(既存、変更なし)
- `sakura_core/my_config.h`

---

## 背景

コマンドパレットのローマ字あいまい検索(`NKMM_COMMAND_PALETTE_ROMAJI_KANJI`)は、
漢字を「読みの先頭1モーラ」だけの単独モーラ辞書(`CKanjiReadingDict`)へ事前展開して
からマッチングする設計になっている。この辞書は網羅的な音訓読みデータではなく
ヒューリスティック(近似)なため、以下のようなクラスの読み漏れが繰り返し報告された:

- 訓読みなのに辞書は音読みのバケットしか持たない(例:「切」は音読み「せつ」の
  「せ」行だが、「切り取り」は訓読み「きり」)
- 辞書が濁音を清音の行にまとめているため、実際は濁音で使われる語に一致しない
  (例:「語」は「ご」だが「こ」行に収録されており、「単語」の「たんご」の
  「ご」に一致しない)
- 2モーラ目が欠けている(例:「検索」の「検」は「けん」まで届かず「け」止まり)

これらは`g_aMultiMoraKanjiTable`(気づいた語だけを都度手動登録する上書きテーブル)
で個別に対応してきたが、根本的には「単独モーラ辞書がそもそも全漢字の正しい読みを
持っていない」という同じ穴が何度も開く構造だった。

## 対応の経緯

1. 「単語」の辞書漏れ報告(`>tango`が「単語の左端に移動」等にヒットしない)を機に、
   コマンドパレットに実在する全コマンド文字列(`sakura_rc.rc`のSTRINGTABLE、
   `F_*`、383件)から使用漢字を洗い出し(173字)、`g_aMultiMoraKanjiTable`へ
   まとめて追加登録した(検/索/単/語/端/切/取/消/折/示/択/動/変/換/連/続/済/表/
   元/現/在/外/部/常/情/時/空/逆/重/除/別/描など、約28字)。
2. 実機での`>クエリ`テスト中に、上記の棚卸しだけでは拾いきれない「2モーラ目欠け」
   (刻/解/複/登/録)を追加で発見・登録した。
3. 上記2つの過程で、音訓読み付きのJIS第1水準漢字辞典(2965字)を一時的に取り込んで
   スクリプトで機械的に突き合わせ、単独モーラ辞書173字ぶんの読みの裏取りを行った
   (取り込みデータ自体はコードには含めていない)。
4. その際、「選択」の「選」がかつて`g_aMultiMoraKanjiTable`に`L"えら"`(選ぶ・
   選んで用)として登録されていたが、実際にコマンドパレットへ出現する文字列には
   「選ぶ」は無く(ダイアログの説明文にのみ存在)、逆に頻出する「選択」への一致を
   壊す退行になっていたことが判明し、`L"せん"`に修正した。
5. 上記の一連の作業を通して「都度手動で気づいて直す」方式の限界(報告が来るまで
   気づけない)が明確になったため、ユーザーの提案により、JIS第1水準の音訓読み
   全件データをコードベースへ正式に取り込み、`g_aMultiMoraKanjiTable`で対応が
   無い漢字についての自動フォールバックとして使えるようにした(本フラグ)。

## テーブルの仕様

`CKanjiReadingTableJIS1.h`は漢字ごとに音読み・訓読みを保持する。

```cpp
struct JIS1KanjiEntry {
	wchar_t			cKanji;
	const wchar_t*	pszOnyomi;	// カタカナ、"・"区切り(無ければ空文字列)
	const wchar_t*	pszKunyomi;	// ひらがな、"・"区切り。"-"より前が活用語幹
};
```

- 複数の読みは中黒`・`区切り(一般的な列挙記法)。
- 訓読みは「活用語幹-送り仮名」表記(例:`か-える`)。これはUnicodeのUnihan
  データベース(`kJapaneseKun`)などでも使われる一般的な慣習であり、特定の
  出典固有の表記ではない。
- ファイル全体が`#ifdef NKMM_COMMAND_PALETTE_ROMAJI_KANJI_JIS1TABLE`で囲まれて
  おり、フラグ無効時はヘッダの中身が空になる。

## 結線(CFuzzyMatchJp.cpp)

`ExpandKanjiReadings()`にフォールバック段を追加した。優先順位:

1. `g_aMultiMoraKanjiTable`(手動、実地検証済み) — 見つかればここで確定
2. `FindReadingFromJIS1Table()`(自動、本フラグ有効時のみ)
3. `CKanjiReadingDict::GetHiraByKanji()`(既存の単独モーラ辞書)

`FindReadingFromJIS1Table()`の選び方は「最初の訓読みの活用語幹(ハイフンより前)、
訓読みが無ければ最初の音読み(カタカナ→ひらがな変換)」という機械的なルールのみ。

## 既知の制限

- 1つの漢字が複数の読みを持つ場合、機械的に選んだ読みが実際のコマンド文字列内での
  使われ方と異なることがある(「選択」の「選」がかつて「えらぶ」を誤って優先して
  いた退行と同種の問題が、本フラグ有効時は他の漢字でも起こり得る)。そうした個別の
  誤りに気づいたら、これまで通り`g_aMultiMoraKanjiTable`へ手動登録して上書きする
  (優先順位1のため、手動登録が常に勝つ)。
- そのため既定では無効にしている。有効化はまだ動作確認していない誤爆パターンを
  増やす可能性があるトレードオフであることを踏まえた上で判断すること。

## 動作確認について

- フラグ無効(既定)でDebug/Release(x64)ともフルビルド0エラーを確認。
- フラグを一時的に有効化してビルドしたところ、新規ヘッダにUTF-8 BOMが無く
  cl.exeがCP932として誤読み込みして構文エラーになる不具合が発覚(既存の
  `CFuzzyMatchJp.cpp`等と同様にBOM付きUTF-8で保存して解決)。修正後は0エラー。
- フラグ有効化時に実機でコマンドパレットを起動し、`kensaku`(検索)・
  `genzai`(現在位置)等の既存クエリが変わらずヒットすることを確認(手動登録が
  優先されるため、既定動作からの意図しない変化が無いことの確認)。
- 最終的にフラグを既定の無効へ戻し、Debug/Release再ビルドで問題ないことを確認。
- `g_aMultiMoraKanjiTable`へ追加した約33字の個別修正は、`>kiri`/`>torikeshi`/
  `>sentaku`/`>idou`/`>henkan`/`>hyouji`/`>genzai`/`>gaibu`/`>tsune`/
  `>jikoku`/`>kaijo`/`>juufuku`/`>touroku`等のクエリで実機確認、または
  `FuzzyMatchJapanese()`内部の正規化結果を直接ダンプして裏取りした。
  途中、PrintWindowによるスクリーンショット取得がウィンドウのリサイズ中の
  1フレームを偶然掴んで「一致していないように見える」テスト側の見かけ上の
  不具合が複数回あったが、いずれも内部トレースで実際には正しく一致している
  ことを確認済み(製品側のバグではない)。
