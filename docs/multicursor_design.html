マルチカーソル編集

VS Code / Sublime Text 風の複数カーソル編集を桜エディタに追加した機能の設計記録。データモデル、各メカニズムの動作原理、既知の制約、そして17回にわたる設計パスの履歴をまとめる。

機能フラグ NKMM_MULTI_CURSOR 実装期間 2026-08-30 〜 08-31 設計パス 20 カーソル上限 NKMM_MULTICURSOR_MAX = 10000

設計方針

プライマリカーソル(既存の CCaret / CViewSelect)は無改変のまま使う。追加カーソルは実体を持たず、プライマリからの固定オフセットとして保持し、必要になった瞬間ごとに実位置へ解決する。編集や選択の実行は、専用のマルチカーソル用ロジックを新規に書くのではなく、各カーソルの解決済み位置に実カーソルを一時的になりすまさせ、既存の単一カーソル用コマンドをそのまま再実行する「コマンド再生」方式で行う。

01 — オフセット方式

追加カーソルの位置・アンカー・希望桁は、いずれもプライマリの対応する値からの相対値としてのみ保持する。絶対位置を直接持つフィールドはひとつもない。

02 — コマンド再生

Command_WCHARやCommand_RIGHTなど既存の単一カーソル実装を、各カーソルの実位置でそのまま再実行する。ラインの折り返し・クランプ・希望桁の計算はすべて既存コードに委譲され、多重実装しない。

03 — Undoはタダ

1コマンドの実行中に開く COpeBlk にN個の COpe が積まれるだけなので、N個のカーソル分の編集が自動的に1回のUndoにまとまる。新規のUndo基盤は不要だった。

この文書の読み方

「中核メカニズム」以降はコードを触る際のリファレンス。末尾の「変更履歴」は、なぜ今の形になったかを時系列で追う付録で、各パスで実際に踏んだ設計ミス・ユーザー指摘・検証方法まで含めて記録している。

01データモデル

CEditView::SExtraCursor ひとつが追加カーソル1個分の全状態。プライマリの3つの異なる基準点(実キャレット位置・希望桁・選択アンカー)それぞれから、独立した相対値を持つ。

フィールド基準点更新されるタイミング
nRelLine / nRelColumnプライマリの実キャレット位置(レイアウト単位)作成時に固定。実際の編集・選択再生(ApplyToAllCursors)が走った回のみ、その結果で更新
nDesiredRelColumnプライマリの希望桁(GetCaret().m_nCaretPosX_Prev)横移動・編集でのみ更新。上下移動でのクランプでは書き換わらない
bHasSelection—そのカーソル自身が選択中かどうか
nAnchorRelLine / nAnchorRelColumnプライマリの選択アンカー(m_sSelectBgn)選択開始時に固定。選択が続く限り、そのカーソル自身のアンカーとして独立に保持

この「オフセットは実際の編集・移動が起きた回にしか書き換わらない」という不変条件が、境界(文書先頭・末尾)をまたいでもカーソル同士の順序・間隔が保たれる根拠になっている。ドキュメント範囲外に解決されたカーソルは、その回の再生対象からも描画対象からも単純に除外され(「非アクティブ」)、オフセット自体はまったく触らない。

02位置の解決

4つの関数がすべて同じ「基準点 + オフセット → 行幅でクランプ → 文字境界へスナップ」というパターンを共有する(CEditView.cpp)。

関数役割
ResolveExtraCursorFromBase共通ヘルパー。基準点+相対オフセットの実位置を算出し、行幅でクランプ、全角文字の中間に着地しないよう LineColumnToIndex/LineIndexToColumn を往復させて境界へスナップする
ResolveExtraCursor上記をプライマリの実キャレット位置基準で呼ぶ。カーソル本体の表示・編集に使う
ResolveExtraCursorAnchorプライマリの選択アンカー基準で呼ぶ。bHasSelection==falseなら無効を返す
ResolveExtraCursorSelectAreaLineアンカー〜現在位置を独立に解決し、プライマリの選択描画と同じ GetSelectAreaLineFromRange に渡す。行をまたぐ選択・折り返しは、この既存ロジックにそのまま乗るぶん新規コード不要

03コマンドの分岐

CViewCommander::DispatchMoveMultiCursor(bSelect, fnMoveOnce) が、移動系コマンドを2つの経路に振り分ける。

高速パス

選択が一切絡まない移動(素の矢印キー等)。fnMoveOnce()をプライマリに対して1回呼ぶだけ。追加カーソルは触らず、次に参照される瞬間に自動追従する

判定

bSelect==true、またはプライマリ・いずれかのextraが現在選択中なら拡張パスへ

拡張パス

ApplyToAllCursors(fnMoveOnce) を呼び、全カーソルそれぞれの実位置で同じコマンドを独立に再実行する

「選択が既にある状態でのShiftなし矢印」も拡張パスに含む — 見た目は移動だが実際は Command_CANCEL_MODE(選択をどちらかの端へ収束させる操作)であり、各カーソル自身の選択状態で再実行しないと、折り返した状態のまま取り残されるカーソルが出る(第十五パスで発見)。

04一括再生ループ — ApplyToAllCursors

タイピング・削除・貼り付けは常にこの経路を通る。選択が絡む移動もここに合流する。プライマリ+全extraをドキュメント降順(下から上)で並べ、実カーソルを使い回して1個ずつ「なりすまし」ながら本物の単一カーソルコマンドを実行する。

// 概念的な流れ(CViewCommander_Edit.cpp)
vAll = [primary, ...活動中のextra]  // 各々の現在位置を解決
sort(vAll, 降順)                    // 未処理カーソルの位置を編集で狂わせないため

nPrimaryGoalOrig  = GetCaret().m_nCaretPosX_Prev   // ループ前に確定
sPrimarySelectOrig = GetSelectionInfo().m_sSelect  // 同上
vExtraAnchor[], vExtraGoal[] を事前計算               // 同じ理由

for slot in vAll:
    実カーソルを slot の位置へ移動
    slot が primary なら 元の選択/希望桁を明示的に復元   // ← 次項で詳述
    そうでなければ そのextra自身のアンカー/希望桁を注入
    fnEditOnce()  // 本物の Command_WCHAR / Command_RIGHT 等をそのまま実行
    結果を(一時的に絶対値のまま)保存

primary を最終位置へ確定
残りのextraを primary の最終位置基準に相対化
MergeOverlappingCursorsIfNeeded()
Redraw()
なぜ毎回「復元」が要るのか

降順ソートのため、プライマリより下の行にextraが1つでもあれば、そのextraはプライマリより先に処理される。extraの番の処理は共有状態(m_sSelectBgn / m_sSelect / m_nCaretPosX_Prev)をそのextra自身の値で上書きするため、「プライマリの番はそのまま触らなくても正しい」という前提は成立しない。プライマリの番が来るたびに、ループ開始前に確定させておいた本来の値へ明示的に戻す必要がある(第十四パスで実際に踏んだ不具合)。

この経路を通るコマンド
操作経由
タイピング・BackSpace・Delete・貼り付け・IME確定常時
Shift+矢印などの選択拡張常時
選択がある状態でのShiftなし矢印(収束)常時
選択が絡まない素の移動高速パスのみ、ここは通らない

05カーソルの統合

CViewCommander::MergeOverlappingCursorsIfNeeded()(第十六パス)。VS Codeの CursorCollection.normalize() と同じ考え方で、重なった/接したカーソルを1個にまとめる。ApplyToAllCursors の末尾、全カーソルの位置が確定した直後にのみ呼ぶ — カーソル同士が実際に独立して動いて衝突しうるのはこの経路だけで、高速パス(プライマリ+全extraの純粋な平行移動)では既存の重なりが増えることは原理的にない。

  • プライマリ+各extraを「アンカー〜現在位置」の範囲として集め、開始位置順に整列
  • 片方が無選択(幅0)なら接触しているだけで統合、両方に選択があれば本当に重なっている場合のみ統合(VS Codeと同じ厳密さ)
  • 方向(アンカー側)は後から追加されたカーソルを優先して引き継ぐ
  • プライマリは実体を消せない singleton のため、統合に関わったら必ずプライマリの識別が生き残る

設定 bMultiCursorMergeOverlapping(既定オン)でオフにできる。

06希望桁の記憶(nDesiredRelColumn)

第十七パスで追加。プライマリには元々 CCaret::m_nCaretPosX_Prev という「希望桁」があり、上下移動で短い行を通過して一時的に桁がクランプされても、長い行に戻れば元の桁へ復元できる。追加カーソルにはこの仕組みが無く、クランプされた実桁がそのまま新しい"本来の"オフセットとして上書きされ続けていた — これが「位置がずれて戻らない」というユーザー報告の実体だった。

絶対位置方式へ全面的に作り直す必要はなく、ApplyToAllCursors が実カーソルを使い回して本物の単一カーソルコマンドを再生しているという既存の仕組みをそのまま利用: 各カーソルの番の前後で GetCaret().m_nCaretPosX_Prev を注入・回収するだけで、桜が元から持っている希望桁ロジック(上下移動でのみ読む、それ以外の操作では即上書き)をそのまま流用できた。「これは上下移動か」を判定する新規コードは一切書いていない。

07描画とIME

キャレットの描画

Win32のネイティブキャレットは1ウィンドウにつき1個までのため、プライマリは既存のまま、追加カーソルは CEditView_Paint.cpp でGDIによる手動描画(FillRect)。OSのキャレット点滅タイマーと同期させると「消灯フェーズで再描画されそのまま不可視になる」問題が出たため、常時表示に統一。色はドキュメントタイプの設定色(COLORIDX_CARET/_IME)をプライマリと同じロジックで再導出している。

選択ハイライト

CColor_Select(view/colors/CColor_Found.cpp)にextra用のキャッシュ(m_vExtraSelectCache)を追加し、既存の1行分キャッシュの仕組みをそのまま複数化。既知のコズメティックな差異として、extraの行末選択が画面右端まで伸びず、実際の最終文字位置で止まる(選択されるテキスト自体は正しい)。

IME

WM_IME_NOTIFY受信時にextra分のRedraw()を追加(色が更新されるよう)。IME再変換(reconversion)はマルチカーソル中は無効化 — 矩形選択時に既にある制約と同じ扱い。文字確定の挿入自体は通常のタイピングと同じ経路で全カーソルへ反映される。

08Undo / Redo

編集の記録自体は新規実装ゼロ。HandleCommandが1コマンドにつき1個のCOpeBlkを開き、InsertData_CEditView/DeleteData_CEditViewの呼び出しは開いているブロックにCOpeを積むだけ — N個のカーソル分の編集が自動的に1回のUndoステップにまとまる。CDocVisitor::SetAllEol(EOL一括変換)が使っているのと同じ既存パターン。

ただし「戻した後の状態」の復元には専用機構が必要だった(第十八パス)。単一カーソル時代のCommand_UNDO/Command_REDOは「ブロック内で最後に処理したOpe」の位置を最終的なキャレット位置として無条件に信頼する実装だった — 単一カーソルなら常にそれで正しいが、ApplyToAllCursorsが1ブロックにN個のカーソル分のOpeを積むと、「最後に処理したOpe」は必ずしもプライマリのものではなくなる(ドキュメント降順で処理するため、画面上どのカーソルが最後に積まれるかはカーソルの配置次第)。

要素役割
COpe::nCursorSlotApplyToAllCursorsが編集直後に付与する識別子。-1=単一カーソル(マルチカーソル無関係)、0=プライマリ、1以上=そのextraの編集時点でのm_vExtraCursors内index+1
CViewCommander::RestoreMultiCursorAfterUndoRedo(pcOpeBlk, nOpeBlkNum, bIsUndo)Command_UNDO/Command_REDO共通の復元処理。nCursorSlotでOpeをスロットごとに束ね、プライマリ・各extraそれぞれ自身の状態(Undo: _Before、Redo: _After)へ明示的に戻し、m_vExtraCursorsを丸ごと再構築する

選択の復元は別の機能フラグNKMM_UNDO_RESTORE_SELECTIONが担う(VS Code同様、「選択→削除」のUndoで削除前の選択状態も復元する)。単一カーソル向けに独立して実装した機能だが、マルチカーソルではRestoreMultiCursorAfterUndoRedoが各スロットのCReplaceOpe::bHadSelectionを読み取り、プライマリ・extraそれぞれの選択を独立に復元する形で合流している。Redoでは選択を復元しない(削除後に選択すべき対象が残らないため、単一カーソル時のRedoも一貫して選択を出さない仕様)。設定bUndoRestoreSelection(既定true)でオフにできる。

見つかった不具合の系譜

①プライマリが復元後に別カーソルの位置に来てしまう(nCursorSlot導入前) → ②プライマリは直るがextraが復元されず一律クリアされる(暫定対応) → ③ユーザーの「設計修正の許可」を受けextra側も同じ機構で正式に復元する形へ書き直し → ④カーソル統合(MergeOverlappingCursorsIfNeeded)を経た選択のUndo復元を個別検証、既存の単一カーソル経路がそのまま正しく処理することを確認。詳細はメモリファイルproject_undo_restore_selection_feature.mdを参照。

09コマンドとキー割り当て

F-code既定キー動作
F_ADD_CURSOR_UPCtrl+Alt+↑最上段カーソルの1行上・同じ桁に新規カーソルを追加
F_ADD_CURSOR_DOWNCtrl+Alt+↓最下段カーソルの1行下・同じ桁に新規カーソルを追加
F_MULTICURSOR_UNDOCtrl+Shift+U直近に追加したカーソルを1個だけ取り消す(テキストのUndoとは別系統)
F_ADD_CURSORS_TO_LINE_ENDSShift+Alt+I選択範囲がまたがる各物理行の行末にカーソルを追加(VS CodeのinsertCursorAtEndOfEachLineSelected相当)

Ctrl+Alt+↑/↓ は元々 F_UP2_BOX/F_DOWN2_BOX(矩形選択の2行ジャンプ)の既定キーだったが、独立コマンドとして新規F-codeを割り当てた(既存コマンドに IsBoxSelecting()で分岐させて二重役割を持たせる案は、キー割り当て設定画面で表示名が実態と食い違う問題があり却下)。矩形選択とマルチカーソルは相互排他 — どちらかの開始が他方を解除する。

F_ADD_CURSORS_TO_LINE_ENDS(2026-09-03追加)は他の2コマンドと異なり、既存のマルチカーソル状態に1個ずつ足すのではなく「今の選択範囲」から新しいマルチカーソル状態を丸ごと作り直す。プライマリ自身の選択(m_sSelect)だけを見て、そこがまたがる各物理行の行末(Command_GOLINEENDのnOption&8相当のアルゴリズムを流用)にカーソルを置く。選択されていなければ何もしない(ErrorBeepのみ)。複数行選択で終端がちょうど次の行の行頭(桁0)にある場合はその行を対象から除く — Shift+↓で行末まで選択したときに、実際には触れていない次の行にまでカーソルが増えるのを防ぐ、VS Codeと同じ扱い。既存の追加カーソルは呼び出し時に全て破棄される(他の追加カーソルが自分自身の選択を持っていても対象外)。

10選択解除の条件

VS Codeの標準的な解除トリガーと突き合わせながら、ユーザーの指示で1つずつ実装した(第九〜十五パス)。

トリガー状態実装箇所
Esc実装済みCommand_CANCEL_MODE
装飾キーなしの通常クリック実装済みCEditView_Mouse.cpp / OnLBUTTONDOWN
検索・置換ダイアログを開く実装済みCEditView::OnKillFocus(下記参照)
フォーカスロス全般実装済みCEditView::OnKillFocus
選択がある状態でのShiftなし矢印確認済み(無改修)選択のみ収束、カーソル自体は残る — 単一カーソルの既存ロジックがそのまま正しく動く
矩形選択の開始実装済みCommand_BEGIN_BOXSELECT ほか
保存など特定コマンドの実行対象外(ユーザー判断)「何か操作すれば勝手に解除されそう」という理由で見送り。再提案しない

検索・置換ダイアログの解除は、当初Command_SEARCH_DIALOG/Command_REPLACE_DIALOG側で個別に明示クリアしていたが、ダイアログ作成(CreateDialogParam)のWM_INITDIALOGで編集ビューが必ずWM_KILLFOCUSを受け取ることを確認し、OnKillFocus側の一括クリアと二重処理になっていたため個別クリアは撤去した(第二十パス、重複整理)。

12既知の制約・対象外

項目内容
残存リスクnRelLineはプライマリとの行数差を固定オフセットとして持つのみ。マルチカーソルの編集操作を介さず、折り返し行数そのものが変わる要因(ウィンドウ幅変更等)が起きると、その瞬間に意味がズレる可能性がある。桁の希望値問題(第十七パス)とは別の問題クラスで、未対応
対象外マウスでのカーソル追加/削除(Ctrl+Alt+クリック等)、「次の一致箇所を選択」(Ctrl+D相当)
対象外マルチカーソル中のIME再変換 — 矩形選択と同じ制約を踏襲
コズメティックextraの行末選択ハイライトが画面右端まで伸びない(選択テキスト自体は正しい) — レガシーROP2描画パスと行末余白の solid-fill 処理には未対応のため
精度の妥協カーソル統合が起きた回、統合に無関係な他カーソルの希望桁も一律リセットされる。安全側(実桁に合わせる)にしか倒れないため実害は小さいと判断し、統合前後の対応関係を個別追跡する精緻な実装は見送った
コズメティックマルチカーソルのUndo復元直後、ステータスバーの選択文字数表示(「N字(M行)選択」)が一瞬古いまま残ることがある。選択データ自体・描画・以後の操作はすべて正しい。原因を一部特定した(CCaret::MoveCursor内部のShowCaretPosInfo呼び出し順)が完全解消には至らず、実害が軽微なため追加調査は見送った(第十九パス)
残存リスクkeybind_presets/Default.key(13節参照)はKeyDataInit[]の既定値と別に手動同期する静的ファイル。今後マルチカーソル系のデフォルトキーを変更したら、このファイルも忘れずに更新すること — 忘れても検知する仕組みはなく、「キー割り当て（実験機能）」タブの「デフォルト」プリセットを選んだときだけ古いキー割り当てに戻ってしまう(2026-09-03に実際に発生・修正)

14変更履歴(全20パス)

2026-08-30〜08-31の2日間で踏んだ設計・修正の全記録。各パスは前のパスの実装が前提になっている。第18〜19パスは機能的にはUndo/Redo(NKMM_UNDO_RESTORE_SELECTION)寄りだが、マルチカーソルのUndo/Redo復元機構(nCursorSlot)そのものを作った回でもあるためここに含める。

01初期実装

Ctrl+Alt+↑/↓でのカーソル追加、Ctrl+Shift+Uでの取り消し、タイピング/BS/Delete/IME確定の一括反映、Esc全解除、矩形選択との排他、GDI手動描画、上限10000。設計段階の懸念だったUndo/Redoは既存COpeBlkの再利用でゼロ新規実装と判明。

02キー割り当ての設計修正

既存F_UP2_BOX/F_DOWN2_BOXへの二重役割案をユーザーが却下(キー割り当て設定画面での表示名不一致)。独立F-codeを新設。新規F-codeが設定画面に表示されるにはFunccode.cppの分類配列・sakura_rc.rcの文字列リソース登録も必要と判明(2箇所を最初漏らして修正)。

03メインメニューへの4箇所目の登録

プルダウンメニューはresource/MainMenu.iniという独自形式の別リソースだと判明、追加登録。

04移動系コマンドの専用フック

通常の矢印移動で追加カーソルが追従しない不具合。DispatchMoveMultiCursorを新設し16個の移動コマンドに配線。

05描画の点滅同期を撤回

OSキャレットの点滅タイマーに同期させると消灯フェーズのまま固まる不具合。常時表示の塗りつぶし矩形に変更。

06境界をまたぐ順序保証の再設計

可変の「保留デルタ」方式で3カーソルの往復移動をトレースしたところ順序が入れ替わる不具合を発見。「プライマリからの固定オフセット、毎回その場で解決」方式に全面変更 — 以後の設計の土台になる。折り返し行数を考慮しない既知の制約が残る。

07横方向のオフセットに拡張

nRelColumnを追加、同じ固定オフセット方式を桁にも適用。移動コマンドは「プライマリを動かすだけ」に単純化できた。

08レイアウト単位への移行

プライマリ自身が短い行でクランプされると、そのクランプ後の桁がextraの基準点として使われてしまう不具合。m_nCaretPosX_Prev(希望桁)を基準にするよう修正し、あわせてロジック単位からレイアウト単位(折り返し対応)へ全面移行。

09Release専用ビルドバグと文字境界スナップ

USE_STRICT_INTがDebugのみ有効なため、.GetValue()がRelease(intの素の型)でコンパイルエラー。ToInt()ヘルパーへ統一。あわせて全角文字の中間に着地するバグをLineColumnToIndex/LineIndexToColumn往復で修正。

10キャレット色をプライマリに追従

ハードコードされた既定色ではなく、ドキュメントタイプの設定色をプライマリと同じロジックで再導出するよう修正。

11選択のミラーリング

extraがプライマリの選択形状を平行移動して再現できるようCColor_Selectを拡張。直後、実際のShift+矢印キーが専用F-code経路(F_RIGHT_SEL等)を通りDispatchMoveMultiCursorを経由していなかった不具合を追加修正。

12選択削除が1文字しか消えない不具合

ApplyToAllCursorsが各カーソルの編集前に無条件で選択解除していた名残バグ。プライマリ自身の削除まで巻き添えで壊れていた。ループ前に選択状態を確定→各カーソルへ翻訳して注入、に修正。

13解除条件チェックリスト(Esc以外)

VS Codeの標準トリガーと突き合わせ、素クリック→検索/置換ダイアログ→フォーカスロス→Shiftなし矢印(無改修で正しいと確認)の順に1つずつ実装。保存等の特定コマンドは対象外と判断。

14選択を「平行移動」から「独立再生」へ全面書き換え

extraの行がプライマリより短いと選択が次の行へ折り返さない不具合。ApplyToAllCursorsを選択移動にも転用し、各カーソル自身の実位置で本物のコマンドを再実行する方式へ全面書き換え。以後の設計の中心的な仕組みになる。

15降順処理でのプライマリ状態の巻き添え

前パス直後の回帰: 1回のShift+→でプライマリが過剰選択。降順ループ中、プライマリより下のextraが先に処理され共有状態を書き換えるため。ループ開始前の状態をプライマリの番ごとに明示的に復元するよう修正。

16折り返し選択キャンセルでの取り残し

前々パス直後の回帰: 折り返した選択を素の←でキャンセルすると、extraが折り返し先の行に取り残される。「選択があるときのShiftなし矢印」もApplyToAllCursors経由に含めるよう修正 — これで解除条件チェックリスト完了。

17カーソル統合 + 希望桁の記憶

VS CodeのmultiCursorMergeOverlappingを調査・移植、設定でオンオフ可能に。続けて「位置がずれて戻らない」報告を調査 — 絶対位置化という当初案をユーザーの指摘で撤回し、プライマリの既存の希望桁機構(m_nCaretPosX_Prev)をextraにも同じ構造で追加する、より小さな修正に着地。ここまでの全機能に対する回帰確認込みで検証済み。

18マルチカーソルUndo/Redoで復元先がプライマリでない不具合

単一カーソル時代のCommand_UNDO/Command_REDOは「ブロック内で最後に処理したOpe」の位置を無条件に信頼する実装だったため、マルチカーソルの一括編集後にUndoすると、プライマリではなくどこかのextraの位置にキャレットが復元される不具合をユーザーが画面写真付きで報告(折り返した3行構成での再現)。当初はCOpe::bIsPrimaryCursorOpe(bool)でプライマリの位置だけを個別復元し、extraは一律クリアする暫定対応にしたが、ユーザーから「設計に修正が必要なら修正してよい」と許可を受け、nCursorSlot(int、プライマリ/どのextraかを識別)へ設計変更し、RestoreMultiCursorAfterUndoRedoで全カーソルを正式に復元する形に作り直した。

19選択削除のUndoで選択状態も復元(NKMM_UNDO_RESTORE_SELECTION)

VS Code同様、「範囲選択→削除」をUndoすると単にテキストが戻るだけでなく選択状態も復元される挙動を、別の機能フラグとして追加。単一カーソル向けの基礎実装(CReplaceOpe::bHadSelection、設定bUndoRestoreSelection)の後、前パスで作ったnCursorSlot機構に選択復元ロジックを合流させ、マルチカーソルでもプライマリ・extra双方の選択が正しく復元されることを確認(統合されたカーソルのUndoも含む)。副次的に、マルチカーソルのUndo/Redoが遠い行の見た目を変えうるのに単一カーソル時代の再描画省略最適化(NKMM_FIX_UNDOREDO)がそれを考慮していない不具合も発見・修正。ステータスバーの選択文字数表示が一瞬古いまま残るコズメティックな副作用は原因を一部特定したのみで残存。

20重複コードの整理

実装が一巡した後、ユーザーの依頼で重複処理の洗い出しを実施。Command_AddCursorUp/Command_AddCursorDown(上下対称なだけの同一ロジック)をAddCursorInDirection(int nDir)に統合。検索/置換ダイアログの明示的なカーソル解除クリアが、ダイアログ作成時に必ず発火するOnKillFocusの一括クリアと二重処理になっていたため撤去。Command_UNDO/Command_REDOにそれぞれ個別に書かれていた復元処理(前パスまでのnCursorSlotベースの約150行、ほぼ同一ロジック)をRestoreMultiCursorAfterUndoRedo1関数に統合 — Undo/Redoの非対称な挙動(m_sSelectBgnを常にSetするかどうか等)を1つも変えないよう慎重に設計し、既存の全回帰テスト(clipboard読み取りによる機能検証)で統合前と完全一致することを確認済み。
