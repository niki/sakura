設計リファレンス — sakura_core

コードフォールディング

文書全体を関数/構造体等のヘッダ行だけのアウトライン表示に折りたたむ機能の設計記録。データモデル、非表示化とコメント色分けを両立させる仕組み、実装過程で発見・修正した実クラッシュの記録をまとめる。

機能フラグ NKMM_CODE_FOLDING 実装日 2026-09-11 既定キー Ctrl+Shift+[ / Ctrl+Shift+] 見つけた実クラッシュ 3件

設計方針

VS Codeの「Fold All」に相当する、文書全体を一括で折りたたむ/展開するトグル動作として実装した。個々の関数を個別に開閉するのではなく、Ctrl+Shift+[(同じ動作のCtrl+Shift+]も)を押すたびに「フルソース」⇔「ヘッダ行だけのアウトライン一覧」を切り替える。既存のアウトライン解析エンジン(CDocOutline)が既に持っている関数/構造体の位置情報を再利用し、折りたたみ専用の構文解析は新規に書いていない。

01 — 全体トグル、個別行ではない

最初はカーソル行だけを開閉する方式で実装したが、「対象の行をfoldするのではなく、全体をfoldしてアウトライン一覧になるようにする」という指示で全面的に作り直した。CLayoutMgr::ToggleFold(CLogicInt)(単一行版)は将来のガターUI向けに残しているが、コマンドからはToggleFoldAll()のみを使う。

02 — 非表示化と色分けの分離

_DoLayout()自体は折りたたみを一切意識せず、常に全行分の色分けを含めて通常通りレイアウトを生成する。折りたたみは、その「後」に非表示にすべき行のCLayoutノードだけを連結リストから取り除く、完全に別の後処理として実装している。

03 — 既存の色分けアーキテクチャに乗る

ヘッダ行の関数名ハイライトは、正規表現エンジンを新設せず、既存のCColor_Select/CColor_Foundと同じ「BeginColorExで行頭のCLayoutを参照して判定する」パターンにそのまま乗せた。

この文書の読み方

「中核メカニズム」以降はコードを触る際のリファレンス。「見つけて修正した不具合」は、実装過程で実際にクラッシュダンプを解析して特定した3件のヒープ破壊系バグの記録で、この機能に限らずCLayout連結リストを直接いじる将来のコードにとっても教訓になる内容を含む。

01データモデル

CDocLine::MarkTypeに追加したCLineFoldedひとつが、行1本分の折りたたみ状態。既存のCLineBookmarked/CLineFuncList等と同じ、docplus流儀の「行に付加する軽量マーク」パターンを踏襲している。

フィールド意味を持つ行役割
m_bFoldable全行この行が折りたたみ開始行(関数/構造体等のヘッダ行)になりうるか
m_bFoldedヘッダ行のみこの開始行が現在折りたたまれているか
m_bHidden非ヘッダ行折りたたみにより非表示になっているか(開始行自身は対象外、常にfalse)
m_nEndLineヘッダ行のみ折りたたみ範囲の終了行(0オリジン)
m_nNameCol / m_nNameLenヘッダ行のみ関数/メソッド名部分の桁位置・文字数(ハイライト用。未特定ならm_nNameCol=-1)

CFoldRangeCalculator::Calculate()が、アウトライン解析結果(CFuncInfoArr)から折りたたみ範囲を算出する。CFuncInfoには開始行しか記録されていないため、深さ(m_nDepth)をキーにしたスタック走査で「次に現れる同じか浅い深さの項目の直前まで」を終了行とみなす。

// 同じか浅い深さの項目が現れたら、それより深い開いたままの項目を
// すべて「直前の行」で閉じる。
while( !vecOpenIndex.empty() ){
    SFoldRange& rOpen = vecResult[vecOpenIndex.back()];
    if( rOpen.nDepth < nDepth ){ break; }
    rOpen.nEndLine = nStartLine - 1;
    vecOpenIndex.pop_back();
}

この汎用アルゴリズムのおかげで、C/C++のような深いネスト構造だけでなく、プレーンテキストのトピック解析のように深さが常に0のフラットな種別でも「次の見出しの直前まで」が自然に折りたたみ範囲になる(対応アウトライン種別参照)。

02非表示化とコメント色分けの両立

最初の実装では、_DoLayout()のレイアウト生成ループ自体に「非表示行はレイアウトノードを作らない」というスキップ処理を入れていた。これは動いたが、隠された行のテキスト(たとえば複数行コメントの開始)が色分けエンジンに一切渡されなくなるため、折りたたみ範囲をまたいだ先の色分けがずれるバグを生んだ。

やめた設計

_DoLayout()のループ内で非表示行をスキップする方式。色分けの状態機械(colorPrev/exInfoPrev)がその行のテキストを一度も見ないまま次の行に進んでしまい、以降の色分けが本来と異なる状態から再開されてしまう。

最終的な設計は、非表示化を完全に別の後処理に分離すること。_DoLayout()自体は折りたたみを意識せず常に全行分を生成し(色分けは常に正しい)、CLayoutMgr::ToggleFoldAll()がその「後」で非表示にすべき行のCLayoutノードだけを連結リストから物理的に取り除く。

_DoLayout( false ); // 折りたたみ非対応、常に全行分の色分けを含めて生成

// その後、非表示にすべき行のCLayoutノードだけを個別に取り除く
CLayout* pNode = m_pLayoutTop;
while( pNode ){
    CLayout* pNodeNext = pNode->GetNextLayout();
    if( cFoldMgr.GetLineFoldHidden( pNode->GetDocLineRef() ) ){
        // … 連結リストから外して delete …
        _TextWidthMultisetErase( pNode ); // 下記「不具合」参照。忘れるとヒープ破壊
        delete pNode;
        m_nLines--;
    }
    pNode = pNodeNext;
}

この設計はCLayoutノードを一旦「無駄に」全部作ってから大半を捨てる(全折りたたみ時は大部分が捨てられる)ため計算量的には非効率だが、折りたたみのON/OFFは高頻度操作ではないため許容している。引き換えに、色分けの正しさを_DoLayout()本体に一切手を入れずに保証できる。

03全体トグル

CLayoutMgr::ToggleFoldAll()が本体。現在の状態は「ヘッダ行以外に表示されている行が1つでもあるか」で判定し、1つでもあれば「折りたたむ」方向、無ければ(ヘッダ行以外すべて非表示なら)「展開する」方向にする。ネストした範囲(クラスの中のメンバ関数等)も区別せず一律に処理する。非表示行に対する多重のSetLineFoldHidden呼び出しはべき等なので安全。

関数役割
CLayoutMgr::ToggleFoldAll()本体。マーク更新→_DoLayout()→非表示行のノード除去、の3段階
CViewCommander::Command_FOLD_TOGGLE()キーバインド(F_FOLD_TOGGLE)のエントリポイント。キャレット位置の調整・画面中央への移動も担当
CSuppressScrBarMarkerForFoldToggleRAIIガード。ToggleFoldAll()実行中、スクロールバーマーカーの背景スレッドを止める(不具合#1参照)

_DoLayout()を直接呼ぶ(DoLayout_Range()による部分再構築ではなく)方式を選んだ理由は単純さと確実性。色分け継続状態の引き継ぎ等が絡む部分再構築の経路は複雑で、折りたたみのON/OFFという低頻度操作にそこまでのコストをかける価値は無いと判断した。

04アウトライン表示中の操作

操作挙動
文字入力・削除・貼り付け等禁止 CEditDoc::IsModificationForbidden()が、通常の読み取り専用時と同じ「編集禁止コマンド一覧」(EIsModificationForbidden)を流用してブロックする
折りたたみ発生時のキャレット非表示になった行にいた場合、直近の手前の表示行(=元いたスコープのヘッダ行)まで遡る。手前に無ければ直後の表示行まで進める
Enter / Tab / ダブルクリックジャンプ 現在のキャレット位置(選択中のヘッダ行)を維持したまま全展開する。Command_FOLD_TOGGLE()をそのまま流用
Esc戻る アウトライン表示に入る直前のキャレット位置(m_ptPreFoldCaretLogic)へ戻して全展開する。Command_FOLD_CANCEL()

ジャンプ・復帰のどちらも、既存のNKMM_FIX_CENTERING_CURSOR_JUMP機構(タグジャンプ等が使うのと同じm_nCenteringCursor++)を流用し、移動先が画面中央付近に来るようにしている。

05ヘッダ行のハイライト

アウトライン表示中、各ヘッダ行の関数/メソッド名の部分だけを検索マーク色(COLORIDX_SEARCH)でハイライトする。戻り値の型・クラス修飾子・引数リストはハイライトしない。

名前の桁位置は正規表現ではなく、アウトライン解析が既に持っている情報だけで求めている。CFuncInfo::m_cmemFuncNameは"Namespace::ClassName::funcName"形式(CType_Cpp.cppのszNamespaceが生成、"::"区切り)なので、最後の区切り以降(短い名前)を取り出し、ヘッダ行の実テキストの中を単純な部分文字列検索(std::wstring::find)するだけ。見つからなければ行全体をハイライトするフォールバックになる。

size_t nSep = sFullName.rfind( L"::" );
std::wstring sShortName = ( nSep == npos ) ? sFullName : sFullName.substr( nSep + 2 );
// sLineText.find(sShortName) で見つかった位置・長さを CFoldManager に記録

ハイライト自体はCColor_OutlineHeader(新規クラス、CColorStrategyの派生)が担当する。CColor_Select/CColor_Foundと同じ「行が変わったら1回だけBeginColorExで判定し、以降はキャッシュを見るだけ」というパターンで、優先順位は選択範囲 > アウトラインヘッダ > 検索マーク > 通常の色分け(SColorStrategyInfo::CheckChangeColor/DoChangeColor)。新規ファイルを増やさず、既存のCColor_Found.h/.cppに同居させている。

06対応アウトライン種別

当初はC/C++限定のMVPとして実装したが、「テキストなどのほかのタイプでもできるようにしたい」という指示で、組み込みのアウトライン解析方式全般に対応を拡大した。CDocOutline::UpdateFoldRanges()が、文書の既定アウトライン種別に応じて対応するMakeFuncList_*/MakeTopicList_*を呼び分ける。

種別対応備考
C / C++ / Java / Perl / VB / Python / Erlang / PL-SQL対応ネストしたクラス/メソッドも深さベースで正しく折りたためる
COBOL / アセンブラ / 階層付きテキスト / HTML / XML / TeX対応
プレーンテキスト対応見出し記号(■○●等、共通設定のm_szMidashiKigou)で始まる行だけがトピックとして認識される(既存仕様、今回変更していない)
ブックマーク一覧 / ファイルツリー / ルールファイル種別非対応コード構造を表すものではないため対象外
プラグイン提供の種別フォールバックプレーンテキストのトピック解析にフォールバックする

07見つけて修正した不具合

実装・検証の過程で、実際にクラッシュダンプ(CrashDumps\*.dmp)を解析して根本原因を特定した3件のヒープ破壊系バグを含む。いずれも「CLayout連結リストを直接操作するコードは、既存の全ての関連キャッシュ/背景スレッドとの不変条件を守らないとヒープが壊れる」という同じ教訓に帰着する。

#1スクロールバーマーカーの背景スレッドとの競合

ToggleFoldAll()内の_DoLayout()実行中、スクロールバーマーカーのバックグラウンド構築スレッド(ScrBarMarker::BuildWorkCallback)が並行して同じCLayout連結リストを参照し、解放済みメモリへのアクセスでヒープを破壊 → 無関係なCOMCTL32内で不可解にクラッシュ。Command_REPLACE_ALLで過去に一度発見・対策済みの同種パターン(CSuppressSrchKeyMarkForReplaceAll)を参考に、CSuppressScrBarMarkerForFoldToggleというRAIIガードで対策した。

#2_TextWidthMultisetErase呼び忘れ

非表示行のCLayoutノードを連結リストから取り除いてdeleteする際、テキスト最大幅キャッシュ(m_multisetTextWidth)からの登録解除を呼び忘れていた。CLayoutMgr.hのコメントで明記されている「CLayout削除時は必ずこのフックを通すこと」という契約違反で、解放済みポインタがキャッシュに残り続け、後で無関係なメモリ確保(mimalloc)がその領域に触れた時に不定動作。

#3スクロールバーマーカーのキャッシュ配列サイズ取り違え

ScrBarMarker::BuildWorkCallback()が、キャッシュ配列のサイズをCLayoutMgr::GetLineCount()(レイアウト行数=折りたたみで激減)で確保していたが、実際の書き込みはCDocLineMgr(論理行数=常に全行分)基準のインデックスで行っていたため、アウトライン表示中に検索するたびに確保領域を超えてヒープへ書き込む、ヒープバッファオーバーフローだった。F2/F3やCtrl+F後の検索実行など、一見バラバラに見えた複数のクラッシュ報告の共通原因だった。

この3件に加えて、オフバイワン(m_nFuncLineCRLFの1オリジン/0オリジンの取り違え)、キャレット位置の取得タイミング、LogicToLayout()の範囲外/NULLフォールバック不足、名前ハイライトの区切り文字の取り違え、といった軽微だが実害のあるバグも見つけて修正した。全件の詳細はchangelog/NKMM_CODE_FOLDING.mdを参照。

08既知の制約

  • 行番号マージンへの+/-アイコン表示・マウスクリックでの折りたたみは未実装(前例の無いUIのため、キーバインドのみで操作する方式に絞った)。
  • 折りたたみ範囲の解析(UpdateFoldRanges)は文書を開いてから最初の1回だけ行う。以降の編集でアウトライン構造が変化しても自動では再解析しない。
  • 個別行単位の折りたたみ(CLayoutMgr::ToggleFold(CLogicInt))は実装済みだが、コマンドからは未使用。
  • ブックマーク一覧・ファイルツリー・ルールファイル種別・プラグイン提供のアウトライン種別は折りたたみ非対応。
  • マクロ(.qjs/.vbs/.pas)から呼び出せるコマンドテーブルへの登録は行っていない。
