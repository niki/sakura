スクロールバーマーカー

検索結果・ブックマーク・キャレット行を垂直スクロールバー上に色付きマーカーとして重ね描きする機能の設計記録。2017年に基本機能が実装され、2026年にスレッドプール化・クリックジャンプ・Explorerテーマ対応など大規模な性能改善とUX強化が集中して行われた、二段階の開発史を持つ。

機能フラグ NKMM_FIX_EDITVIEW_SCRBAR 初版 2017-06-09 性能改修 2026-08-06〜17 中核クラス ScrBarMarker

設計方針

マーカー専用のカスタムコントロールは作らず、標準のSCROLLBARウィンドウ(Explorerテーマ適用済み)の上から、ウィンドウプロシージャのサブクラス化とGDIの半透明合成(AlphaBlend)だけでオーバーレイ描画する。ドキュメント全体の走査(キャッシュ「作成」)と、実際にピクセルへ描く処理(「描画」)を明確に2段階へ分離し、それぞれ専用のスレッドプールワーク(PTP_WORK)に投げることで、編集操作のたびに走る重い処理をUIスレッドから追い出す。

01 — 素のスクロールバーへの上乗せ

ネイティブSCROLLBARコントロールをそのまま使い、GetDCで取得したHDCへ非同期に直接矩形を上書きする。WM_PAINT自体はフックしない。

02 — 作成と描画の分離

全行スキャンしてvLines_キャッシュを作るBuildと、そのキャッシュを画面に反映するだけのDrawを別スレッドプールワークに分離。色変更・ホバー再描画など「描くだけでよい」更新はDrawだけで済ませる。

03 — 数値チューニングより方式変更

デバウンス・OpenMP並列化・重複描画スキップ・スレッドプール化・色キャッシュなど、性能問題は都度その場しのぎの数値調整ではなく、根本原因(スレッド生成コスト、レジストリ多重読み込み等)を特定してから方式ごと変更する形で潰されてきた。

この文書の読み方

「中核メカニズム」以降はコードを触る際のリファレンス。「パフォーマンス施策の変遷」は、2026年に集中して行われた性能改修が何が原因でどう直ったかを時系列で追う付録で、同種の重い編集フック(Command_INSTEXT等)を新設する際の注意点としても読める。

01表示されるマーカー種別

実装されているのは3種類のみ。検索結果・ブックマークの2種はScrBarMarker::vLines_(uint32_t配列)に、下位28ビット(NKMM_SCRBAR_LINEN_MASK)へレイアウト行番号、上位4ビット(NKMM_SCRBAR_MAGIC_MASK)へ種別ビットをORで詰めるビットパッキング方式で格納する(1行に両方あれば両ビットが立つ)。

02コントロールの実体とテーマ

垂直スクロールバーは標準のSCROLLBARウィンドウクラス(CreateScrollBar(), CEditView_Scroll.cpp)。NKMM_SCRBAR_SYSTEM_STYLE(2026-07-18)によりSetWindowTheme(hwnd, L"Explorer", NULL)でExplorer風の細いビジュアルスタイルを適用した上で使う(テーマ無効環境では従来の見た目にフォールバック)。

// CEditView_Scroll.cpp
CUxTheme::getInstance()->SetWindowTheme( m_hwndVScrollBar, L"Explorer", NULL );
// ホバー解除時にマーカーを再描画するためサブクラス化
g_pOldVScrollBarWndProc = (WNDPROC)::SetWindowLongPtr(
    m_hwndVScrollBar, GWLP_WNDPROC, (LONG_PTR)VScrollBarWndProc );

VScrollBarWndProcによるサブクラス化(SetWindowLongPtr(GWLP_WNDPROC, ...))でWM_MOUSEMOVE/WM_MOUSELEAVE/WM_TIMER/WM_LBUTTONDOWN/WM_DESTROYを横取りし、それ以外はCallWindowProc()で元のプロシージャへ素通しする。マーカー描画そのものはWM_PAINTをフックせず、GetDC(hwnd)で取得したHDCへスレッドプール経由で直接矩形を上書きする、ネイティブのペイントとは独立したオーバーレイ方式。

クリックジャンプ・ホバー再描画のどちらも、このNKMM_SCRBAR_SYSTEM_STYLEによるサブクラス化が前提で、それが無効な場合は動作しない。

03描画パイプライン

編集・ブックマーク・検索の各操作から最終的に画面反映までの経路は次の通り。

要求

編集/ブックマーク/検索操作 → SB_Marker_Clear() がデバウンスタイマー(150ms)をリセット

作成

入力停止後 ScrBarMarkerDebounceTimerProc → SB_Marker_Build() → ScrBarMarker::Build()。変更なければ即描画要求、無ければSubmitThreadpoolWork(pBuildWork_)

スキャン

BuildWorkCallback()が全行スキャンしてvLines_キャッシュを再構築 → SB_Marker_DrawRequest() → PostMessage(WM_APP_SCRBAR_PAINT)

描画

WM_APP_SCRBAR_PAINTハンドラ → SB_Marker_Draw() → SubmitThreadpoolWork(pDrawWork_) → DrawWorkCallback()がGetDC→AlphaBlendMyRect()で上乗せ描画

描画完了はPostMessage(WM_APP_SCRBAR_ENDPAINT)で通知され、そのハンドラがWaitForDraw(false)でハンドルの後始末を行い、検索ヒット件数を検索ダイアログへ反映、UpdateWindow(m_hwndVScrollBar)で締めくくる。

「キャッシュ作成」と「描画」を分けているのは、色変更やホバー時の再表示などキャッシュ自体は変わらず画面に描き直すだけでよい更新を、全行再スキャンを伴わない軽量パスにできるようにするため(05節のホバー再描画がこの分離を利用している)。

04色分けと半透明合成

色はRegKey(NKMM_REGKEY)(レジストリキーSoftware\sakura-niki)経由で3つの値名から読み込まれる(ScrBarMarker::RefreshColorCache())。

clrSearchCache_ = si::ColorString::ToCOLORREF(
    RegKey(NKMM_REGKEY).get_s(_T("EditViewScrBarFoundColor"), NKMM_SCRBAR_FOUND_COLOR));
clrMarkCache_ = si::ColorString::ToCOLORREF(
    RegKey(NKMM_REGKEY).get_s(_T("EditViewScrBarMarkColor"), NKMM_SCRBAR_MARK_COLOR));
clrCursorCache_ = si::ColorString::ToCOLORREF(
    RegKey(NKMM_REGKEY).get_s(_T("EditViewScrBarCursorColor"), NKMM_SCRBAR_CURSOR_COLOR));

色を都度レジストリから読むのは重いため(06節で発覚した経緯)、ScrBarMarkerのコンストラクタとBuildWorkCallback()(実際に文書が変化した時だけ走る経路)でのみ再読込し、DrawWorkCallback()はメンバのキャッシュ値を読むだけになっている。

描画自体はCGraphics::AlphaBlendMyRect(rc, color, alpha)により、GDIのAlphaBlend()APIで半透明合成する。1×1の単色ビットマップを転送元とし、指定矩形サイズまで引き伸ばして合成する(ピクセル単位のアルファは持たず定数アルファのみ)。不透明度はNKMM_SCRBAR_MARK_ALPHA(既定220/255)。半透明化(2026-08-10)は、つまみ(サム)に重なったマークが自然に透けて見えるようにするためで、それ以前はFillSolidMyRect()による不透明な塗り潰しだった。

検索マークは横幅いっぱい(高さ2px程度)の細い横線、ブックマーク・カーソル行マークはnCxVScroll/3四方程度の小さな正方形として描かれる。

05位置計算

DrawWorkCallback()内のfnLineToYラムダ、およびHitTest()内の同一式(当たり判定を表示とズレさせないためコメントで明記して同じ式を複製している)がドキュメント行数→スクロールバー座標変換の核心。

auto fnLineToY = [=](uint32_t ln) -> int {
    return nBarTop +
        (bEnable ? ((int)((float)(ln & NKMM_SCRBAR_LINEN_MASK) / ToInt(nAllLines) * nBarHeight))
                 : ((int)((float)(ln & NKMM_SCRBAR_LINEN_MASK) /
                          ToInt(pEditView->GetTextArea().m_nViewRowNum) * nBarHeight)));
};

nBarTopはスクロールバー上端の矢印ボタン分のオフセット(SM_CYVSCROLL)、nBarHeightはGetScrollBarInfo()で取得した実際のトラック領域の高さから上下の矢印ボタン分を差し引いた値。bEnable(スクロール可能=全行数が表示行数を超えている)かどうかで分母を「全レイアウト行数」か「画面に表示できる行数」に切り替える — スクロール不要でバー自体が実質フル表示のときの位置ズレ対策。単純な線形補間であり、折り返しを考慮した「レイアウト行」ベースの座標系を使う。

マーク矩形のサイズ・位置補正(fnDrawMarkAtY)は、矩形の中心が計算Yに来るようy - height/2し、上下矢印ボタンの領域にはみ出さないようマージン補正を行う。

06クリック・ホバー操作

クリックでジャンプ(NKMM_SCRBAR_MARKER_CLICK_JUMP, 2026-08-10)

VScrollBarWndProcのWM_LBUTTONDOWNハンドラが、クリックY座標に最も近い検索/ブックマークのマーク行(許容誤差max(DpiScaleY(4), 4)px)をScrBarMarker::HitTest()で探索し、見つかれば_SB_Marker_HitTestAndJump()経由でAddCurrentLineToHistory()(ジャンプ前の位置を履歴登録)→MoveCursorSelecting()でその行へジャンプする。メッセージを消費し、既定のスクロールバー動作(ページスクロール/サム位置ジャンプ)は行わない。

  • つまみ(現在の表示位置を示すサム)の上をクリックした場合は、マークジャンプよりつまみのドラッグ操作を優先する(HitTest()冒頭でxyThumbTop〜xyThumbBottom範囲内なら即falseを返す) — マークがたまたまつまみに重なった時にスクロールバーがつまめなくなる事態を防ぐ設計
  • マークの無い位置のクリックはCallWindowProc()で素通しし、既定動作(ページスクロール等)に任せる

ホバー時の再描画(NKMM_SCRBAR_MARKER_HOVER_REDRAW, 2026-08-10)

Explorerテーマのホバー(フェード)アニメーションでスクロールバー全体が自前描画され、マーカーが数百msかけて消されてしまう問題への対策。WM_MOUSEMOVEで非ホバー→ホバーへの遷移を検出した時点で即1回SB_Marker_CallPaint()し、以後50ms間隔・最大8回(400ms)のタイマーで_SB_Marker_HoverRedraw()(軽量パス、SetScrollInfo更新なし)を繰り返し呼んでマークの再表示を維持する。WM_MOUSELEAVEでもマーカー再描画とタイマー停止を行う。

キーボード操作によるマーカー専用ショートカットは無い(通常のカーソル移動・検索コマンド(F3等)がマーカー更新を間接的にトリガーするのみ)。

07パフォーマンス施策の変遷

2017年のキャッシュ化から2026年のスレッドプール化まで、その場しのぎの数値調整では再発するたびに閾値を動かすだけになっていた問題を、根本原因を特定してから方式ごと変更する形で1つずつ潰してきた記録。

01キャッシュ化2017-06-10

全行スキャン結果をvLines_配列にキャッシュし、スクロールのたびに再スキャンしないようにした。

02バックグラウンドスレッド化

キャッシュ「作成」と「描画」をそれぞれ別スレッドで実行(当初は_beginthreadexによる都度スレッド生成)。

03入力デバウンス化2026-07-28

Clear()は即座に再構築せずSetTimer(..., 150ms)をリセットするだけにし、連続入力(タイプ入力)が止まってから1回だけBuild()する(IDT_SCRBAR_MARKER_DEBOUNCE, SCRBAR_MARKER_DEBOUNCE_MS=150)。ただし描画抑制中(SetDrawSwitch(false)、ReplaceAll等のバルク編集)は例外的にデバウンスせず同期Build()を呼ぶ(競合防止)。

04ReplaceAll激重バグの修正2026-07-28

Command_INSTEXTが編集毎に無条件で呼ぶSB_Marker_Clearが、ReplaceAll中に1行ごとにスレッド生成+Sleep(10)を引き起こし、20,000行の置換で200秒以上かかっていた。GetDrawSwitch()==false中はWaitForBuild/WaitForDrawで既存スレッドを止めた上で即returnするガードを追加(changelog/NKMM_FIX_SCRBAR_MARKER_REPLACEALL_PERF.md)。

05水平スクロールバーの再描画スキップ判定バグ修正2026-08-06

SetScrollInfoスキップ判定の更新漏れを修正(changelog/NKMM_FIX_EDITVIEW_SCRBAR_HWIDTH_SKIP.md)。

06競合クラッシュ修正・OpenMP並列化・重複描画スキップ2026-08-09

SB_Marker_BuildThreadとChangeCurRegexp()の競合クラッシュ、WM_APP_SCRBAR_PAINTのブロッキング待ちを解消。「折り返しなし」かつ「正規表現でない」検索に限り、BuildWorkCallbackの全行スキャンループを#pragma omp parallel for schedule(dynamic, 4096)で並列化(折り返しありはLogicToLayout()の共有キャッシュ競合、正規表現は単一共有エンジンCEditView::m_CurRegexpの競合のため対象外)。さらに、行番号順処理でY座標がほぼ単調増加である性質を利用し、直前と同じYなら描画をスキップする重複描画スキップも追加(ヒット数が数万〜数十万件になる巨大ファイルでFillRect呼び出しが爆発するのを防ぐ)。

07スレッドプール化・クリックジャンプ・半透明化・CPU対策2026-08-10

編集の度に_beginthreadexでOSスレッドを新規生成し起動直後にSleep(10)していたのを、CreateThreadpoolWork/SubmitThreadpoolWorkによる常駐ワーカーへの投入方式に変更しスレッド生成コストとSleep(10)を排除。取りこぼし防止のためbRebuildPending_/bRestartRequestDrawThread_のコアレッシング機構を導入したが、その後発覚したTOCTOUレースをmtxBuildState_/mtxDrawState_(std::mutex)で修正した。同日、クリックジャンプ・ホバー再描画・AlphaBlend半透明化を追加し、ホバー中のCPU使用率対策を2段階で実施: 第一段はホバー中50ms間隔の再描画タイマーが毎回SetScrollInfo(redraw=TRUE)(ネイティブ全面再描画、テーマアニメーション再トリガー)を発生させ続けていたのをDraw(bUpdateScrollInfo=false)の軽量描画パスへ分離。第二段はDrawWorkCallback()が呼ばれる度に色設定をレジストリから都度読んでいた(1回で12回のレジストリAPI呼び出し)ことと、ホバー中ずっとタイマーを回し続けていたことの2点が原因と判明し、色キャッシュ導入とNKMM_SB_HOVER_REDRAW_MAX_TICKS(既定8回=400ms)でのバースト後自動KillTimer()で解消した。CGraphics側でも、呼び出しの度にCreateCompatibleDC/CreateCompatibleBitmapしていたのをインスタンス生存期間中使い回す方式に変更(changelog/NKMM_FIX_EDITVIEW_SCRBAR_THREADPOOL.md / NKMM_FIX_SCRBAR_MARKER_INTERACTION.md)。

08水平スクロールバーの自動非表示2026-08-17

各行の文字数がウィンドウ幅に収まっている間はバー自体を非表示にし、その分テキスト表示領域を広げる(内容がウィンドウ幅を超えたら自動的に再表示)。従来は常にバーの領域を確保した上で不要なときはグレーアウトするだけだった。マーカー描画そのものではなく水平バー周りの表示最適化。

08設定項目

共通設定ダイアログや.iniには、この機能に対応する設定項目は一切無い。機能自体(検索/ブックマーク/カーソル行表示、クリックジャンプ、ホバー再描画)のON/OFFはmy_config.hのコンパイル時フラグでのみ制御可能で、実行時にユーザーが無効化する手段は無い。

項目公開方法既定値

ブックマークの色同上、値名EditViewScrBarMarkColor#ff0032

不透明度・クリック許容誤差・デバウンス時間・ホバータイマー周期/上限実行時設定不可 — すべてソースコード中の定数220/255、max(DpiScaleY(4),4)px、150ms、50ms×8回

色の3項目はUIから設定する手段が無く、regedit等での直接操作、またはアプリ側がRegKeyラッパー経由で読むだけの「隠し設定」的な位置づけになっている。

09既知の制約・対象外

項目内容
未対応CreateThreadpoolWork()が失敗した場合(メモリ不足等)のエラーハンドリングは未実装。pBuildWork_/pDrawWork_がnullptrのままSubmitThreadpoolWork()されるとクラッシュする(旧_beginthreadex実装も同様に未対応だったため、既存と同水準のまま据え置き)
未検証スレッドプールへの投入が正しく行われるか、再構築要求の取りこぼしが実際に起きないか、ウィンドウ多数オープン時にスレッド数が増えなくなったか、といった実機での網羅的な動作確認は行われていない(NKMM_FIX_EDITVIEW_SCRBAR_THREADPOOL.md)
未解決開いているウィンドウ数に応じてReplaceAllが遅くなる現象が残っている。原因候補として共有メモリ(DLLSHAREDATA)経由のウィンドウ間同期等が挙げられているが、「実運用で数十枚のウィンドウを開いたまま大量置換を繰り返す状況はまず起きない」として既知の制限扱い
スコープ外Undo履歴の段数上限が無く無制限に蓄積し続ける設計上の問題を発見したが、エディタ本体の改善は今回のスコープ外として見送られた
既知の副作用検索ハイライトの一時無効化(CSuppressSrchKeyMarkForReplaceAll)により、ReplaceAll実行中(および完了直後の一瞬)は編集画面上の検索文字列ハイライト表示も無効化される。実害はほぼ無いと見られるが完全には否定していない
対象外変更行/diffマーカー、エラー行(Lint等)マーカーは未実装。マジック値のビット割り当てに拡張の余地はあるが、明記された計画は無い
