絵文字カラーフォント

GDIでは単色でしか描画できないCOLR/CPAL形式のカラーグリフ(絵文字)を、Direct2D/DirectWriteでオーバーレイ描画する機能の設計記録。ZWJ絵文字合字・肌色修飾子・キーキャップの結合表示、絵文字フォントの固定指定UIまでを含む。初回調査時にコードとコメントの食い違いが複数見つかり、2026-08-31にコメント側を実挙動へ合わせて修正した。

機能フラグ NKMM_FIX_COLOR_FONT 初版 2026-07-17 合字対応 2026-08-16〜17 中核クラス CColorFontRenderer

設計方針

既存のGDI描画パイプラインには一切手を入れず、そのまま残す。GDIの描画結果の直後に、カラーグリフだけをDirect2D/DirectWriteで追加描画する「オーバーレイ」方式を採る。Direct2D/DirectWriteが利用できない環境(DLL不在など)では自動的に何もせず、従来通りのGDI描画のみにフォールバックする。

01 — GDIは変えない

通常のテキスト描画・選択範囲反転・ルーラー描画はすべて既存のGDI経路のまま。カラーグリフの描画位置・フォント・色をキューに積み、1行分のGDI描画が確定した後にだけ上乗せする。

02 — 合字はレンダリングのみ

ZWJ絵文字の合字化は「描かれる絵」だけを1グリフへ統合し、CNativeW::GetSizeOfChar()等のカーソル移動・文字数計算コードには一切手を入れない — フルのグラフェムクラスタ対応より侵襲性の低い選択。

03 — 失敗は必ず個別描画へ

合字シェーピングの成功判定は「1ラン・1グリフ」のみ。それ以外は全て失敗として扱い、変更前と完全に同じ1文字ずつのフォールバック描画に戻る — 最悪でも退行(regression)にはならない設計。

この文書の読み方 — 食い違いは2026-08-31に解消済み

本機能は2026-07-17に初版が入り、2026-08-16〜17にZWJ合字・絵文字フォント固定指定UIが集中して追加された。この文書の初版作成時の調査で、コード中のコメントが説明する設計意図と、実際の挙動が一致していない箇所が複数見つかった(07節)。机上の設計ミスではなく、短期間に段階的な変更が重なった結果コメントの更新が追いつかなかったことによるもので、2026-08-31にコメント側を実挙動に合わせて修正済み(ロジック・UI挙動は無変更)。デバッグログの残置(09節)のみ、コメントではなく実コードの整理が要る項目として未対応のまま残っている。

01GDIとDirectWriteの共存

CFigure_Text::DrawImpがGDIで通常描画した直後に、figures/CFigureStrategy.cppが描画位置(rcColorCell)・使用HFONT・前景/背景色を取得しCEditView::TryQueueColorGlyph()へ渡す。この時点ではまだ描画せず、キューに積むだけ(GDIの描画結果はそのまま画面に残る)。

1行分の全GDI描画(選択範囲反転・ルーラーも含む)が終わった直後、CEditView_Paint.cppのOnPaint末尾で次の順に呼ぶ。

CGlyphAtlasCache::getInstance()->FlushQueue(gr, nGlyphQueueMark);  // 先に通常グリフのアトラス転送
FlushColorGlyphQueue(gr);                                          // その後カラーグリフのオーバーレイ

この順序は重要 — オーバーレイは「確定した下地のピクセルの上に重ね描きする」ことを前提にしている。

CColorFontRenderer::FlushQueue()の内部では、Sakuraの画面バッファ(DDB)へ直接BindDCすると一部描画が反映されない不具合があったため、自前の32bpp DIBセクション(m_hdcOffscreen)へ一旦BitBltでコピー→Direct2Dで描画→結果をセルごとにBitBltで実HDCへ書き戻す、という迂回構成になっている。

D2D1/DWriteはLOAD_LIBRARY_SEARCH_SYSTEM32でSystem32からのみロードし、ポータブル配布時のDLL探索順序ハイジャック対策が明示的に取られている(CColorFontRenderer.h)。IDWriteFactory2(Windows 8.1相当)が無い環境では初期化が失敗し続け、機能全体が自動的に無効化される。

02COLR/CPALレイヤー取得とフォールバック解決

1. フォントフェイス化

GetOrCreateFontFaceEntry(hFont)でHFONT→IDWriteFontFace2変換(キャッシュ付き)、IsColorFont()判定

2. 本文フォント優先

本文フォント自身がグリフを持ち、かつカラーフォントならそのまま採用(GDI描画結果を信用)

3. フォールバック解決

グリフが無い、またはVS16強制指定がある場合はResolveFallbackHFONT()で代替フォント解決

4. レイヤー取得

FetchColorLayers()がIDWriteFactory2::TranslateColorGlyphRunを呼び、最大8レイヤー(SColorGlyphCell::MAX_LAYERS)を取得。パレットインデックス0xFFFFは前景色扱い

ResolveFallbackHFONT(): 絵文字フォントが固定指定されていればまずFindSpecifiedEmojiFont()を試し、無ければIDWriteFontFallback::MapCharacters(GDIのSystemLinkに頼らない自前解決)を使う。返るfScale(x-height基準の見た目合わせ)をフォントサイズに反映した上、GDI実測幅(fAdvanceX)に収まるよう「縮小→再測定」を8回、その後「1刻みずつ拡大し直す」フェーズで余白を削る反復収束ロジックを持つ。

フォント全体はカラーでもグリフ単体はモノクロなことがある

絵文字フォント内の普通の英数字グリフ(キーキャップの数字部分など)には COLR/CPAL レイヤーが無く、TranslateColorGlyphRunがDWRITE_E_NOCOLORを返しFetchColorLayers()がfalseになる。この場合に諦めて何も描かずreturnするのではなく、白黒の輪郭グリフとして前景色で描画するフォールバックへ必ず落とす(bGotColorLayers判定)。絵文字フォント固定指定機能の追加によって数字がSegoe UI Emoji側へ強制解決されるようになった際に発覚したバグで、修正済み。

03ZWJ絵文字合字

CEditView::TryQueueColorGlyph()(CEditView_ColorFont.cpp)で、直前の文字がZWJだったか・自身がZWJ/VS15/VS16/肌色修飾子/結合用囲み記号(キーキャップ)かを判定し、該当すれば即座にキューへ積まずm_vPendingClusterCalls(SPendingGlyphCall配列、CColorGlyphCell.h)へ保留する。プレーンテキストはこの判定に一切引っかからず、変更前と完全に同じ即時パスを通る(バッファリングのオーバーヘッド無し)。

区間が確定するとFlushPendingCluster()が起動する。要素が1個だけなら合字化の余地なし→即フォールバック。2個以上かつ「フォント/前景色/背景色/ベースラインオフセットが揃っている」かつ共通設定の合字チェックがONの場合のみTryShapeCluster()を試行する。

TryShapeCluster()(実際のDirectWriteテキストシェーピング): クラスタ全体のテキストをIDWriteTextLayoutに流し込み、自作のIDWriteTextRenderer(CGlyphRunCaptureRenderer)経由でDrawGlyphRunをフックし、実際のグリフランを記録するだけの最小実装で「本物のGSUB合字が起きたか」を検証する。

成功/失敗判定 — 1ラン・1グリフのみ成功

成功条件はnRunCount==1 && nGlyphCount==1。複数ランに分かれた(フォールバック途中でフォントが切替わった)場合や、1ランのglyphCountが1でない(フォントのGSUB合字テーブルに該当組み合わせが無く複数グリフのまま)場合は失敗として扱い、呼び出し側は1文字ずつのフォールバック描画に戻る — 最悪でも変更前とバイト単位で同一の挙動になる。成功時は実際にシェーピングで使われたフォント(本文フォントとは限らない)をConvertFontFaceToLOGFONTでLOGFONT化し直し、既存のFetchColorLayers経路へそのまま乗せる。

キーキャップ合字の右端欠け対策

合字化された絵文字グリフはフォントのem正方形サイズで描画されるため、見た目上ほぼ正方形になる。キーキャップ(数字+VS16+結合用囲み記号)のように、構成文字が全てBMP内の細い桁ばかりのクラスタでは、各セル幅を単純に合算しただけでは正方形に足りず右端が欠けて見える問題があった。対策として、行の高さを下限にrcUnion.rightを拡張して正方形を確保している(2026-08-16、コミット173b02673で追加、現在のコードに反映済み)。

04VS/ZWJ/肌色/キーキャップの扱い

判定関数対象所在
IsZWJCharU+200D(Zero Width Joiner)CEditView_ColorFont.cpp
IsVariationSelectorCharU+FE0E(VS15、テキスト表示指定)/ U+FE0F(VS16、絵文字表示指定)同上
IsFitzpatrickModifierU+1F3FB〜U+1F3FF(肌色修飾子)。ZWJ不要でそのまま付着同上
IsCombiningEnclosingKeycapU+20E3(結合用囲み記号、キーキャップ)同上
IsInvisibleFormatCharVS15/VS16/ZWJが単独で来た場合、背景色で塗り潰すだけ(レイヤー無し)のセルを返すCColorFontRenderer.cpp

IsInvisibleFormatChar()はGDIのSystemLinkフォールバックが無意味な四角/記号(tofu)を描いてしまうのを消すために存在する。

bForceEmojiPresentation(VS16直後判定)はCFigureStrategy.cppで「行末を超えて読まないよう境界を確認」しつつ次の1文字を覗き見て決定し、TryGetColorLayersへ渡す。本文フォントがそのコードポイントのモノクロ持ち駒を持っていても、VS16があれば強制的にカラー(絵文字)フォント解決へ回す — ❤/✏️/⚠️のような両対応(dual-presentation)記号を確実に色付きにするための仕組み。

05絵文字フォント指定UI

本文フォント起点のシステム自動フォールバックに任せず、絵文字解決に使うフォントを固定指定できる機能(2026-08-16追加)。共通設定「全般」タブ→描画グループに配置。

設定項目データ構造既定値
絵文字フォントを固定指定するCommonSetting_Window::m_bUseEmojiFontTRUE
絵文字フォント本体m_lfEmoji(LOGFONT、lfFaceNameのみ使用)"Segoe UI Emoji"
プレビュー用ポイントサイズm_nEmojiPointSize110(11.0pt)
絵文字の合字を有効にするm_bUseEmojiLigatureFALSE要注意

NKMM_COLOR_FONT_EMOJI_FONT_NAME(my_config.h、既定L"Segoe UI Emoji")は初回起動時にのみm_lfEmojiへ初期投入される既定値であり、以後はユーザー設定(sakura.ini)が優先される。

FindSpecifiedEmojiFont()は指定フォント名をシステムフォントコレクションから検索し、対象コードポイントにIDWriteFont::HasCharacter()で該当グリフがあるかを確認した上で返す。フォントが未インストール、または該当文字を持たない場合はNULLを返し既存のMapCharactersフォールバックへ自動的に戻る — 指定フォントが他の環境に存在しなくても壊れずに劣化する設計。

「未選択=システム自動選択」状態はGetConfiguredEmojiFontName()で判定する。

if( !sWindow.m_bUseEmojiFont || 0 == sWindow.m_lfEmoji.lfFaceName[0] ){
    return NULL;  // システムの自動選択にフォールバック
}

ラベル表示(UpdateEmojiFontLabel())は、チェックOFF、またはONでもフォント名が空(未選択)の場合「(システムの自動選択)」に切り替わる — CPropCommon::SetFontLabelの空文字列規約をあえて使わず、この機能専用に判読しやすいメッセージを用意している。

UI構成: 「絵文字フォントを固定指定する」チェック、「絵文字フォントの選択」ボタン(押下でフォント選択ダイアログ、選ぶと自動的にチェックON)、選択中フォント名のラベル、「絵文字の合字を有効にする」チェックの4点セット。既存の「タイプ別フォント」と異なり、フォント指定チェックはOFFでも常に操作可能(システム任せへいつでも戻せるようにする、という明示的な要件)。

06撤回された設計・未実装のキャッシュ

グリフ幅拡張(D2D横方向変形) — 撤回済み、現在も未採用

VS16の桁ぶんまで絵文字を拡大して隙間を埋める案を2回試した(均一拡大は縦方向にはみ出す、横方向だけのD2D変形は見た目が不自然)。いずれも撤回され、現在も撤回されたまま — VS16の桁はIsInvisibleFormatCharにより単に背景色で塗り潰されるだけになっている。連続する強制カラー絵文字の間に視認できる隙間が残るが、現状は許容として据え置かれている。

グリフ単位のビットマップキャッシュは実装されていない

CAtlasPagePoolは元々、通常テキスト用CGlyphAtlasCacheが内部に持っていたページプール管理コードを、CColorFontRenderer側のカラーグリフとも将来共用できる想定で切り出した共通部品。しかしCColorFontRenderer.cpp/.hのどこにもCAtlasPagePoolへの参照は無く、この抽出時にもColorFontRenderer側への適用は行われなかった。つまりColorFontRenderer自身にはグリフ単位のキャッシュが一切無く、毎回Direct2Dで描き直している。パフォーマンス上の共通点は「フォントフェイスキャッシュ」「ブラシキャッシュ(上限64件で丸ごとクリア)」「フォールバックHFONTキャッシュ(プロセス寿命)」というフォント単位/色単位のキャッシュのみで、いずれもグリフ単位ではない。フォント世代カウンタCViewFont::s_nGenerationはNKMM_FIX_COLOR_FONTとNKMM_FIX_GLYPH_ATLAS_CACHEの両方でインクリメントを共有しており、フォント再作成時に両方のキャッシュが無効化される点だけは確かに連携している。2026-08-31 コメント修正済み — CAtlasPagePool.h/CGlyphAtlasCache.cppの該当コメントは「共用している」という誤った現在形の記述から、上記の経緯(共用を想定して抽出したが未適用のまま)を正確に説明する記述へ更新した。

「グリフをビットマップとしてキャッシュする(BitBlitキャッシュ)」という設計案についても、コミット履歴上そのような実装が存在した痕跡は見当たらない。CColorFontRendererは一貫して「毎フレーム、その場でDirect2Dへ描画→BitBltで転送」という方式のみで運用されている。

07コードとコメントの食い違い(2026-08-31 解消)

短期間(2026-08-16〜17)に段階的な変更が重なった結果、コメントの更新が追いついていない箇所が複数残っていた。2026-08-31にコメントのリファクタリングを行い、以下はいずれもコメント側を現在のコードの実態に合わせて修正済み(ロジック・UI挙動そのものは変更していない)。

解消済み「絵文字フォント」OFFで「合字」チェックが操作不能になる点の説明不足

2026-08-17のコミット(12d9a6fbe)で、「絵文字フォント」チェックをOFFにすると「合字」チェック自体がEnableWindow(..., m_bUseEmojiFont)で無効化(グレーアウト)されるようになったが、CShareData.cpp側のコメントは「独立の設定」とだけ書かれ、このUI連動に触れていなかった。ロジック(TryShapeCluster()は指定フォントが無くても本文フォント起点で合字を試みる)自体は今も独立のままで、変更したのはコメントのみ: CShareData.cppの既定値コメントと、CPropComGeneral.cppのEnableWindow呼び出し2箇所(OnInitDialog/IDC_CHECK_USEEMOJIFONTハンドラ)に、「これは分かりやすさのためのUI上の連動であり、チェックが無効化されてもm_bUseEmojiLigatureの値自体はクリアされない」という説明を追記した。

解消済みm_bUseEmojiLigatureの既定値コメント

CShareData.cppのコメントが「既定で有効にする」のままだったのを、実際の代入値(FALSE、コミットd3554d8b4)に合わせて「既定はOFF(合字化で見た目が変わることに驚くユーザーが出ないようオプトインにした)」へ書き換えた。CommonSetting.hのメンバコメントにも既定値の注記を追加した。

解消済みCAtlasPagePoolの「共用」表現

06節参照。「共用している」という現在形の誤りを、「共用を想定して抽出したが実際には未適用」という経緯の説明へ修正した。

デバッグログの残置(未対応)

CColorFontRenderer.cpp内に複数箇所OutputDebugStringWによる[ColorFont]ログが残っている(フォールバックフォント解決失敗時、オフスクリーンサーフェス確保失敗時、FlushQueueのBindDC/EndDraw結果など)。changelog/NKMM_FIX_COLOR_FONT.md末尾で「リリース前に整理(削除またはデバッグビルド限定化)を推奨」と明記されているが、これはコメントではなく実コードの整理を要する項目のため今回のコメントリファクタリングでは対象外とし、既知の制約として残した。

changelog/NKMM_FIX_COLOR_FONT.mdにも2026-08-16〜17の合字対応・絵文字フォント固定指定・2026-08-31のコメント整理について追記済み(10節)。

01初期実装2026-07-17

GDI描画はそのまま残し、Direct2D/DirectWriteでCOLR/CPALカラーグリフだけを追加でオーバーレイ描画する基本設計を実装。

02グリフアトラス、プール処理を分離2026-08-16 07:06

通常テキスト用CGlyphAtlasCacheのページ管理ロジックをCAtlasPagePoolとして抽出。コミットメッセージに「絵文字の合字対応」とあるが、実際には結合(合字)そのものはまだ実装されていない(コミットメッセージ自身に「（実際には結合はしていない）」と明記)。

03ZWJ/VS15/VS16/肌色修飾子の合字対応(表示のみ)2026-08-16 08:06

TryShapeClusterによるクラスタリング・シェーピング機構を実装。「表示のみ、カーソル移動は未対応」という設計上の制約はこの回から一貫している。

04キーキャップ合字対応2026-08-16 08:53

IsCombiningEnclosingKeycapを継続判定に追加。この直後、右/下端が欠けて見えるクリッピング問題が2件見つかり、幅の正方形化・フォントの行高さフィットの2段階で修正された(03節)。

05絵文字フォント固定指定・UI設定化2026-08-16 13:20

ハードコードされた定数(NKMM_COLOR_FONT_EMOJI_FONT_NAME)を、共通設定「全般」タブのUI(チェック+ボタン+ラベル)として実行時変更可能にした。「未選択=システムの自動選択」という明示状態を持たせることをユーザーから要件として指定された。

06合字の初期値修正2026-08-16 13:26

m_bUseEmojiLigatureの既定値をFALSEに変更。
