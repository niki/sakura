セッション復元

終了時に開いていたファイル(未保存の変更内容を含む)を、次回起動時に自動的に復元する機能の設計記録。「タブ1枚=別プロセス」というsakura特有のアーキテクチャ制約が、保存トリガー・復元トリガー双方の設計をどう規定したかを中心にまとめる。2026-08-27〜28のセキュリティ監査で見つかった修正、および2026-09-01のコメントリファクタリングの内容も含む。

機能フラグ NKMM_SESSION_RESTORE 初版 2026-08-14 バッファ復元 NKMM_SESSION_RESTORE_BUFFER OSシャットダウン対応 2026-08-15

設計方針

v1スコープはタブグループ構成・ウィンドウ位置を対象外とし、ファイルパス一覧のみを保存・復元する。事前調査で、グループ情報を持たないフラットなファイルパス一覧をsakura.exe f1 f2 f3として素朴に再起動時へ渡すだけで、既存の複数ファイル起動ロジック(1本目のウィンドウに残りが自動的にタブ合流する)がそのまま働くことを確認済みなため、この方式を採用した。

01 — 単一の集約点に一本化

保存はCControlTray::CloseAllEditor()という「閉じ始める前に全ウィンドウ一覧が取れる」唯一のタイミングに一本化する。per-windowのWM_DESTROYは連鎖クローズ時にきょうだいの情報が既に消えているため不採用。

02 — 既存経路の再利用

復元は保存したパス一覧を、通常のコマンドライン複数ファイル起動と同じ形(先頭をm_fi、残りをm_vFiles)に注入するだけ。グループ合流・OpenFiles()といった既存処理を素通しで再利用し、新規の復元専用ロジックを作らない。

03 — 安全側に倒す

OSシャットダウンのレース条件、iniのパストラバーサル、固定長バッファのオーバーフローなど、判断に迷うケースは常に「確認ダイアログを出す」「保存前に切り詰める」「読み込みを拒否する」といった安全側の挙動へ倒す。

この文書の読み方

「保存経路」「復元経路」「バッファ復元」は仕組みそのもののリファレンス。「実態と修正」は2026-08-27〜28のセキュリティ監査と2026-09-01のコメント整理で見つかった、コードとコメントの実態を記録した節。今後この機能を触る際は、セキュリティ修正節にある2種類のバリデーション(パス検証・切り詰め)を壊さないよう注意すること。

01マルチプロセス制約

サクラエディタの「タブ」は1プロセス内の複数ドキュメントではなく、タブ1枚=別プロセスのsakura.exeが共有メモリ(DLLSHAREDATA/CAppNodeManager)経由でグループ化(EditNode.m_nGroup、IDは1始まり)されて見た目上まとまっているだけ。

この制約が2つの帰結を生む。

  • 「今開いている全ファイル」の取得にはCAppNodeManager::GetOpenedWindowArr()(プロセス横断、共有メモリ経由)が必須
  • 「本当にアプリが終了するタイミング」は1プロセスのWM_DESTROYだけでは判断できない — 複数ウィンドウ(=複数プロセス)が連鎖的に閉じる場合、自分が最後の1枚になった時点では既に他のウィンドウが配列から消えている

この2点が、保存トリガーを「per-window WM_DESTROY」ではなく「CloseAllEditor()という単一の集約点」に置く根拠になっている(02節)。

02保存トリガー — CControlTray::CloseAllEditor()

GetOpenedWindowArr(&pWndArr, TRUE)で、閉じ始める前の完全な一覧をタブの実際の表示順(bSort=TRUE、EditNode::m_nIndex順)で取得する。当初はbSort=FALSE(共有メモリ配列上の生成順に近いスロット順)だったため、タブをドラッグで並べ替えた状態で「すべて閉じる」を行うと復元後にタブの並びが変わる不具合があり、修正された。

「実質的に全終了か」の判定

nGroup==0

「ファイル→サクラエディタの終了」「編集の全終了」。常に全グループ対象

nGroup!=0

特定グループだけを閉じる操作(グループ化タブのタイトルバー×は実機確認上こちらを通る)

判定

現在開いている全ウィンドウがそのグループに属する(=他に残るグループが無い)なら、結果的に全終了と同じとみなす

上記いずれでもない場合(他のグループが残る)は何もしない。

n≥2ルール

ユーザー要望による追加ルール: 一括で閉じようとしているウィンドウが2枚以上のときだけ実ファイル一覧を保存する。n==1の終了は通常の単一ファイル起動と同じ意味なので、空リストで明示的に上書きし、以前の(複数ウィンドウ終了時の)古いセッションが残り続けないようにする。

per-window WM_DESTROYを断念した理由

当初CEditWndのWM_DESTROYでm_nEditArrNum==1を見て保存する設計だったが、RequestCloseEditor()が同期的SendMessage(MYWM_CLOSE)で1枚ずつ順に閉じるため、複数ウィンドウが連鎖的に閉じる場合、最後の1枚が自分のWM_DESTROYで数を確認する時点で既に他のきょうだいウィンドウは配列から消えている(自分1枚分の情報しか取れない)。単発の1ウィンドウ直接クローズでは問題ないが、一括終了では機能しない。

この副次フックは現在も残っており、CloseAllEditor()を経由しない個別クローズで自分が最後の1枚になる場合に、古いセッションが紛らわしく残らないようその場でセッションを明示的にクリアする役割を担う。

03OSシャットダウン対応

2026-08-15追加。各ウィンドウ(=別プロセス)が独立してWM_QUERYENDSESSIONを受け取るため、CloseAllEditor()のような単一の集約点が存在しない。CEditWnd::DispatchEvent()のハンドラで以下の方式により対応する。

  • 最初にWM_QUERYENDSESSIONを受け取ったウィンドウが、まだ誰も閉じ始めていない時点での全ウィンドウ一覧からセッションを保存する。この保存処理はCloseAllEditor()と共通化され、CControlTray::SaveSessionSnapshot(pWndArr, n)として切り出されている
  • 「自分が最初か」の判定は、単純なif/代入(読んでから書く)ではなくInterlockedCompareExchange()でアトミックに行う。WM_QUERYENDSESSIONが複数プロセスへ本当に1つずつ順番に配送される保証はOS実装依存でコード側では保証できないため、万一2つ以上のプロセスがほぼ同時にこの分岐へ入っても実際にスナップショットを取るのは1プロセスだけになる
  • 拒否時(このウィンドウがシャットダウンを拒否した場合)はフラグをFALSEへ戻す。WM_ENDSESSION(wParam==FALSE=キャンセル)でも念のため同様に戻す(二重の安全策)

他のウィンドウが拒否してシャットダウン自体がキャンセルされた場合、既に閉じてしまったウィンドウは戻らない(サクラエディタ既存の挙動、対応範囲外)。

04二重発火防止 — m_bSessionHandledByCloseAll

DLLSHAREDATA::m_sFlagsの一時共有フラグ(iniには保存しない)。CloseAllEditor()とper-window WM_DESTROYの個別クリアが二重に走って上書き合戦にならないよう調停する。

タイミング値
SaveSessionSnapshot()末尾(保存/クリア完了直後)TRUE
CloseAllEditor()のRequestCloseEditor()(同期的に全ウィンドウを閉じ切る)が戻った後FALSE
WM_QUERYENDSESSIONの拒否時FALSE
WM_ENDSESSION(wParam==FALSE、キャンセル)時FALSE

per-window WM_DESTROY側の個別クリアは、このフラグが立っていれば何もしない。

05復元トリガー — CNormalProcess::InitializeProcess()

以下すべてを満たす場合のみ、保存されたファイル一覧をCCommandLineの内部ファイルリスト(先頭をm_fi、残りをm_vFiles)に注入し、既存の複数ファイル起動経路をそのまま再利用する。

条件目的
m_bRestoreSession機能自体がONであること
GetFileNum()==0 && m_fi.m_szPath==""コマンドラインでファイル指定が一切無い。1ファイルだけの起動はm_fiに入りm_vFilesは0件になるため、GetFileNum()だけでは判定不十分
m_nEditArrNum==0他にsakuraウィンドウが1つも起動していない(真のコールドスタート)。「新規ウィンドウを開く」操作や二重起動時に誤って復元が発動しないようにする
!IsNoWindow() && !IsDebugMode()
&& !IsGrepMode() && !IsGrepDlg()		「通常のファイル編集ウィンドウ」ではない特殊な起動(-NOWIN=/-DEBUGMODE=/Grep結果表示/Grepダイアログ単体起動)を復元対象から除外する

すべて満たした上でLoadSessionFileList()が保存済みエントリを読み、SetFilesForSessionRestore()で注入する。

06永続化とSaveShareData()の落とし穴

CShareData_IO::SaveSessionFileList/LoadSessionFileListは、DLLSHAREDATAや通常のShareData_IO_2(設定の読み書き本体)を経由せず、sakura.iniの[Session]セクション(_Session_Counts、Session[NN].szPath等)へ独自に読み書きする。

SaveShareData()が[Session]を丸ごと消す

CShareData_IO::SaveShareData()(→ShareData_IO_2(false))はiniファイル全体をゼロから組み立てて書き直す(ReadProfile()せず、既知のキーだけを書いてWriteProfile()で丸ごと上書き)。これは通常の設定保存では正しいが、[Session]のように独自に書き込むセクションは既知のキーではないため跡形もなく消される。SaveShareData()が呼ばれるのはCControlTray::OnDestroy()(トレイウィンドウのWM_DESTROY、アプリ終了時のただ一箇所)で、CloseAllEditor()で[Session]を書いた直後にこれが走り、書いたそばから消える不具合が実機で発生した。対策としてOnDestroy()内でSaveShareData()の直前にLoadSessionFileList()で退避し、直後にSaveSessionFileList()で書き戻す。

空リストの扱いに注意: LoadSessionFileList()は0件のときfalseを返すため、戻り値で「退避が必要か」を判定すると、n==1終了時の「明示的な空クリア」が「退避不要」と誤判定され、書き戻されずセクションごと消えてしまう不具合が実機で発生した。bRestoreSessionがONなら常に(空でも)無条件で書き戻すよう修正済み。

07未保存内容の復元(NKMM_SESSION_RESTORE_BUFFER)

NKMM_SESSION_RESTOREはファイルのパス一覧だけを保存し、次回起動時にそのパスを普通に開き直す。ディスク上のファイルを再読込するだけなので、未保存の変更や無題(一度も保存していない)バッファは復元されない。本機能は全終了時にバッファの中身そのものを退避し、次回復元時に(保存していなくても)その中身を復元できるようにする。

未保存内容が平文でプロファイルフォルダ配下に一時的に残るという性質があるため、既存の「セッションの復元」チェックボックスとは別の明示的なオプトインチェックボックスとして分離してある。

プロセス間の橋渡し

01節と同じ「タブ=別プロセス」制約がある。セッション復元時、先頭ファイルは自プロセス内で開かれるが、残りはCNormalProcess::OpenFiles()がCControlTray::OpenNewEditor2()経由で実際にsakura.exeを新規プロセスとしてCreateProcessする。バッファの中身そのものを直接プロセス間で渡すことはできず、渡せるのはコマンドライン文字列だけ。

ダンプ

全終了時、変更ありのウィンドウへMYWM_DUMPBUFFERを同期送信。CWriteManager::WriteFile_From_CDocLineMgr()でSessionBuffers\配下(UTF-8+BOM、拡張子.swp)へ生ダンプ

橋渡し

別プロセスへは新設スイッチ-BUFRESTORE="<パス>"で橋渡し。先頭ファイル(自プロセス内)はCCommandLine::SetFilesForSessionRestore()が直接セット

復元

CDocFileOperation::RestoreBufferOverlay()がCReadManager::ReadFile_To_CDocLineMgr()を直接呼び、InitDoc()/SetFilePathAndIcon()をあえて呼ばずにバッファ内容だけを上書きする

InitDoc()(変更フラグをfalseへリセットしてしまう)とSetFilePathAndIcon()(ドキュメント識別情報=現在のファイルパスの変更)をあえて呼ばない理由は、現在のドキュメント識別情報を変えずにバッファ内容だけを上書きし、明示的に変更フラグを立てるため。これらを呼んでしまうと、名前付きファイルなのに復元後のバッファが「保存済み(未変更)」扱いになってしまい、未保存内容の復元という目的自体が崩れる。

non-consumed設計(消費しない)

復元時にバックアップファイルを削除する「消費型」にはしていない。理由は2つ。

  • 既存のパス一覧復元も、LoadSessionFileList()は読むだけで復元時に[Session]を消しておらず、次回全終了時の上書きまで残る設計。バッファ版もこれに揃え、「復元は読み取り専用、掃除は保存時の全消去のみ」という単一の掃除ポイントに統一した
  • 消費型だと、復元してから一度も完全終了せずにクラッシュ/強制終了して再度コールドスタートした場合、2回目は既にバックアップファイルが無く復元できない。非消費型なら同じ未保存内容が毎回復元される=復旧機能としてより堅牢

唯一の掃除ポイントはClearSessionBufferDir()で、新しいバックアップファイルをダンプする前にSessionBuffers\の中身を無条件で全消去してから書き直す(元は参照されなくなったファイルだけ消す reconcile 方式だったが、早期return時の残骸問題で無条件全消去へ変更)。削除に失敗した場合(ファイルロック等)は無視する。

トレードオフ: 復元してから次に完全終了するまでの間、未保存内容の平文バックアップがSessionBuffers\に残り続ける。

08レース条件の発見と対処(2026-08-15)

OSシャットダウン対応(03節)とバッファ復元機能の組み合わせを精査したところ、保存確認の抑制ロジックに理論上のデータロス系のレース条件が見つかった。

問題

当初の抑制条件(閉じるときに「変更を保存しますか？」を出さない条件)は!IsValidPath() && m_bSessionHandledByCloseAll && m_bRestoreSessionBufferだった。CloseAllEditor()経由なら、全ウィンドウのダンプを完了させてから各ウィンドウのOnFileClose()を呼ぶ(単一プロセス内の同期ループ)ため問題は起きない。しかしOSシャットダウン経由の場合、各ウィンドウ(=別プロセス)が個別にWM_QUERYENDSESSIONを受け取り、OSがその配送順序をシリアライズする保証はない。そのため、代表ウィンドウが他ウィンドウBのバッファをダンプし終える前に、B自身のWM_QUERYENDSESSIONが先に処理され、BのOnFileClose()が「m_bSessionHandledByCloseAllが立っている=どうせ退避される」と誤判定して確認を抑制し、そのまま閉じてしまう競合があり得た。この場合Bの内容は実際にはまだダンプされておらず、未保存の変更がそのまま失われる。

対処: 「誰かが保存処理を始めた」ことしか示さない共有(複数プロセス)フラグm_bSessionHandledByCloseAllだけに頼るのをやめ、「自分の内容が実際にダンプされたか」を示すローカルな(プロセス内、CEditDocの)フラグm_bSessionBufferCapturedを新設した。

  • MYWM_GETFILEINFOハンドラ(SaveSessionSnapshot()が各ウィンドウへ問い合わせる際、ループ先頭で必ず呼ばれる)で、まずfalseにリセット — 過去の中断された試みのダンプ実績が今回の試みに紛れ込むのを防ぐ
  • MYWM_DUMPBUFFERハンドラで、ダンプに実際に成功した時だけtrueにする
  • 抑制条件を!IsValidPath() && m_bSessionHandledByCloseAll && m_bSessionBufferCapturedに変更

m_bSessionBufferCaptured単独ではなくm_bSessionHandledByCloseAllとの組み合わせで見ている点が重要: 後者は全終了処理の開始/終了(成功・中断いずれも)で確実にFALSEへ戻るため、無関係な後日の個別クローズで過去のダンプ実績が誤って抑制に使われることもない。

パストラバーサル対策(20260827、LoadSessionFileList)

Session[NN].szBuf(バックアップファイル名)は[Session]セクションの独自I/O経由で、他プロセスによる書き換えや手編集が可能な信頼できない入力。保存時の前提(ファイル名のみ、パス区切りなし)を読み込み側でも独立に検証する。

// LoadSessionFileList() 内
bool bBufNameSafe = !strBufName.empty()
    && strBufName.find_first_of(L"\\/:") == std::wstring::npos
    && strBufName != L"." && strBufName != L"..";

\///:のいずれかを含む、または値そのものが./..の場合は拒否し、entry.bModifiedをfalseへ落として通常のパスオープンへフォールバックする。検証しないと、..等によるSessionBuffers\外への任意ファイル読み込み(→ユーザーの保存操作による任意ファイル上書き)を許してしまう。

固定長バッファへの生_tcscpy置換(20260828)

ini/コマンドライン(-BUFRESTORE=)由来でサイズ上限の無い文字列を、サイズ上限のある固定長バッファへコピーする箇所が計4箇所、境界チェック無しの_tcscpyのままだった。いずれも_tcsncpy_s(..., _TRUNCATE)へ置換し、規定長を超える場合はabortさせず切り詰める方式に統一した。

関数ファイルコピー先
SetFilesForSessionRestore()CCommandLine.hm_fi.m_szPath
SaveSessionSnapshot()CControlTray.cppDLLSHAREDATA::m_sWorkBuffer::m_szDumpBufferTargetPath_MYWM_DUMPBUFFER

OpenFiles()CNormalProcess.cppfi.m_szBufRestorePath

DLLSHAREDATAは共有メモリ上の固定長構造体であり、ここでオーバーフローすると隣接する他フィールドを破壊しうる(終了処理中に発生するとクラッシュや破損データの書き込みにつながる)。切り詰めを選んだのは終了処理を止めない(abortしない)ため。

12既知の制約

項目内容
対象外タブグループ構成・ウィンドウ位置はv1スコープ外(ユーザーとの相談で決定)
未対応強制終了(タスクキル等、WM_DESTROYを経由しない終了)では保存されない
トレードオフバッファ復元は非消費型のため、復元してから一度も完全終了せずに長期間使い続けた場合、その間ずっと未保存内容の平文バックアップがSessionBuffers\に残る
未対応大きく変更したファイルの全終了は、その場でファイルサイズ分のダンプI/Oが発生する。サイズ上限は設けていない
割り切りClearSessionBufferDir()の削除失敗(ファイルロック等)は無視する。「タイミングが悪いときは仕方ない」という明示的な判断
